## 前提

本稿はパッケージ追加のPRを対象とします。
特に、`nix-init`で比較的簡単に扱えるGolangあるいはRust製のCLI/TUIツールを念頭に置いています。

なお、本稿はあくまで個人的に「引っかかりやすかった」と感じたポイントをまとめたものに過ぎません(筆者はまだ5件ほどしかmerge経験がありません)。
一番大事なのは[CONTRIBUTING.md](https://github.com/NixOS/nixpkgs/blob/master/CONTRIBUTING.md)をしっかり読むことです。
併せて[pkgs/README.md](https://github.com/NixOS/nixpkgs/blob/master/pkgs/README.md)、[各言語のドキュメント](https://github.com/NixOS/nixpkgs/tree/master/doc/languages-frameworks)などにも目を通しておくことをおすすめします。

## 最初に行う基本的な流れ

まずはNixpkgsをforkし、ローカルにcloneします。
そのうえで、本家のNixpkgsを`upstream`として登録しておく必要があります。

```bash
git remote add upstream git@github.com:NixOS/nixpkgs.git
git fetch upstream
```

最新の`master`をベースにして、新しいブランチを切ります。

```bash
git switch --create hello/init upstream/master
```

ブランチ名に厳格なルールは存在しないようですが、CONTRIBUTING.mdの例では`update-hello`のような形式が示されています。
私はよく`<package>/init`としていますが、用途が伝わる名前であれば問題ないでしょう。

ブランチを切ったら、リポジトリのルートで`nix-init`を実行します。
`nix-init`はGitHubなどのリポジトリURLから`package.nix`の雛形を自動生成してくれるツールです。

@[card](https://github.com/nix-community/nix-init)

`pname`/`version`/`src`/`hash`/`vendorHash` (Go) や`cargoHash` (Rust) などを、ある程度埋めた状態で出力してくれます。

```bash
nix run github:nix-community/nix-init
```

新しいパッケージは原則として`pkgs/by-name/<2文字prefix>/<package-name>/package.nix`へ配置します(`nix-init`なら自動でやってくれます)。
`hello`であれば`pkgs/by-name/he/hello/package.nix`となります。

ただし、`nix-init`はあくまで雛形生成ツールです。
生成された定義をそのままPRに出すのではなく、以下の各項目を必ず人間の目で確認してから提出します。

## `__structuredAttrs = true;`が設定されているか確認する

Nixpkgsのstdenvドキュメントには、次のように明記されています。

> All new top level packages must enable `__structuredAttrs`.

すなわち、新規のトップレベルパッケージは`__structuredAttrs`を有効化しなければなりません。

これを有効化すると、derivationの属性がJSONファイルとシェルスクリプトとしてビルダーへ渡されます。
リスト型の属性（`ldflags`や`cmakeFlags`など）はbash側で配列として展開されるため、空白を含む値も安全に渡せます。
一方で、環境変数として「エクスポート」したい属性は`env`属性配下に定義する必要があるため、`CGO_ENABLED`などを直接渡している既存テンプレートからの流用時には注意が必要です(？)。

最新バージョンの`nix-init`で生成した場合は最初から付いてきます。
古いテンプレートを流用したときなどは抜けやすいので、念のため確認しましょう。

参考: <https://github.com/NixOS/nixpkgs/blob/master/doc/stdenv/stdenv.chapter.md#var-stdenv-__structuredAttrs>

## `versionCheckHook`を登録する

`nix-init`が生成した雛形には、`versionCheckHook`がついてません。
CLIパッケージでは、ビルド成果物が実際に正しいバージョンを名乗っているかを確認するため、`versionCheckHook`を登録しておくと安全です。

`versionCheckHook`は`preInstallCheckHooks`に`versionCheckPhase`を追加するhookです。
ビルドしたバイナリに`--version`または`--help`を渡し、その出力中に`${version}`の文字列が含まれているかを検査します。
含まれていなければビルドは失敗します。

```nix
{
  lib,
  stdenv,
  versionCheckHook,
  # ...
}:

stdenv.mkDerivation (finalAttrs: {
  # ...

  doInstallCheck = true;
  nativeInstallCheckInputs = [ versionCheckHook ];

  # ...
})
```

`meta.mainProgram`が設定されていれば、その実行ファイルが自動的に検査対象となります。
`PATH`や`HOME`などの環境変数を必要とするプログラムでは注意が必要です。
`versionCheckProgramArg`や`versionCheckKeepEnvironment`を調整するか、代替として[`testers.testVersion`](https://nixos.org/manual/nixpkgs/stable/#tester-testVersion)の利用を検討します。

参考: <https://github.com/NixOS/nixpkgs/blob/master/doc/hooks/versionCheckHook.section.md>

## 引数は登場順にする

derivationの関数引数の順番は、関数本体での登場順に並べるのが慣例です。
`nix-init`の出力も基本的にこの順序になっています。
ただし、後から`buildInputs`などを追加した際にうっかり崩れることもあります。
レビューでもよく指摘されるポイントなので、PRを出す前に上から順に目視で揃えましょう。

```nix
{
  lib,           # 関数本体で最初に lib.* を使うので最初
  stdenv,        # 次に stdenv.mkDerivation
  fetchFromGitHub, # 次に src で fetchFromGitHub
  versionCheckHook,
  nix-update-script,
}:
```

## Goの場合`ldflags`が正しいか確認する

Goの多くのプロジェクトは、`-ldflags "-X main.Version=..."`の形式でビルド時にバージョン文字列をバイナリに埋め込んでいます。
元リポジトリのMakefileやgoreleaserの設定を確認し、同等の値が`ldflags`で渡されているかをチェックします。

```nix
{
  ldflags = [
    "-s"
    "-w"
    "-X main.Version=${finalAttrs.version}"
    "-X main.Commit=${finalAttrs.version}"
  ];
}
```

`-X`で指定する変数のパスはプロジェクトごとに異なります。
`main.Version`の場合もあれば`github.com/owner/repo/cmd.version`のようなフルパスの場合もあるため、必ず元リポジトリのビルドスクリプトを確認します。
ここがずれていると`versionCheckHook`が空文字列を見て失敗するため、両者をあわせて確認するのが効率的です。

参考: <https://github.com/NixOS/nixpkgs/blob/master/doc/languages-frameworks/go.section.md#var-go-ldflags>

## `meta.description`が正しく書けているか確認する

`meta.description`には、`pkgs/README.md`で厳格な規則が定められています。

- 簡潔に、1文で記述すること
- 大文字で書き始めること
- 定冠詞（the）や不定冠詞（a/an）で始めないこと
- パッケージ名で始めないこと
- より一般的に、パッケージ名に言及しないこと
- 末尾にピリオド（その他の句読点を含む）を打たないこと
- 事実に基づいた情報を提供すること
- 主観的な表現を避けること

元リポジトリのREADMEから引用した文をそのまま貼ると、いずれかに違反している可能性が高いです。
特に「A blazing fast ...」のような主観的・宣伝的な表現や、文末のピリオドはレビューで頻繁に指摘されるので、提出前に読み返すと安全です。

詳しくは<https://github.com/NixOS/nixpkgs/blob/master/pkgs/README.md#meta-attributes>を参照してください。

なお、`meta`まわりでは以下も併せて確認しておくと、レビュー往復を減らせます。

- `meta.license`が元リポジトリのライセンスと一致しているか
- `meta.homepage`が設定されているか
- `meta.mainProgram`が設定されているか（実行ファイルが1つだけのCLIなら基本的に必須）
- `meta.maintainers`に自分が含まれているか（新規パッケージでは必須）

## コミットが規則に沿っているか確認する

コミット規約は<https://github.com/NixOS/nixpkgs/blob/master/CONTRIBUTING.md#commit-conventions>および<https://github.com/NixOS/nixpkgs/blob/master/pkgs/README.md#commit-conventions>に書かれています。

新規パッケージ追加の場合、コミットメッセージは次の形式にします。

```text
hello: init at 0.1.0
```

- 先頭に`(pkg-name):`プレフィックスをつける（CIの自動ビルド対象を決めるためにも重要）
- 末尾にピリオドを打たない
- 1論理単位につき1コミットにまとめる（`squash`を活用）

レビューのフィードバックを反映する際は、新しいコミットを積みません。
代わりに`git commit --amend`または`git rebase -i`で既存コミットに統合してから、`git push --force-with-lease`します。
こうすることで、最終的にマージされる履歴が綺麗な1コミットに保たれます。

はじめてのコントリビュートの場合は`maintainers/maintainer-list.nix`に自分の情報を登録する必要があるため、コミットは2つになります。
このときの順序とメッセージにも決まりがあります。

```text
maintainers: add <handle>
hello: init at 0.1.0
```

- 自分をmaintainerに追加するコミットを先に置く
- メッセージは`maintainers: add <handle>`とする

参考: <https://github.com/NixOS/nixpkgs/blob/master/CONTRIBUTING.md#commit-conventions>
